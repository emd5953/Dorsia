## SharedArray and timestamp evaluation

- Inspected `loadtest/drop.js`: token data is loaded through `new SharedArray('drop member tokens', () => JSON.parse(open(...)))`; each VU reads only its own indexed row. The workload remains 5,000 VUs, one iteration per VU, random 0–10 second delay, and same-key hold/confirm retries. `timestampMillis()` changes the seeder's space separator to `T`, truncates fractional seconds to milliseconds, and `Date.parse()` is then used to wait until `opens_at` plus the delay.
- SharedArray mutation: in the disposable copy, replaced the SharedArray expression with the prior `JSON.parse(open(...))`, then ran `make drop-seed && make drop-run`. The k6 process exited 137 while initializing 1,146/5,000 VUs at 0% scenario progress; Make reported `Error 137`. The original `drop.js` was restored immediately afterward. This reproduces the local memory sensitivity and supports that the SharedArray change bites; it does not prove the Ubuntu runner can complete.
- Baseline diagnostic with the restored SharedArray: `make drop-seed` then `make drop-run` initialized all 5,000 VUs, completed all 5,000 iterations, and summarized 50 confirmed, 4,950 sold out, 0 server errors, 0 unexpected, hold p95 277.25 ms, confirm p95 477.90 ms. `make drop-run` failed its strict confirm threshold (`Error 99`). `make drop-verify` then passed SQL verification and `wallet:reconcile` (1,003 accounts checked, global sum 0, zero unbalanced transactions, zero accounts with drift). This was one macOS Docker Desktop diagnostic and is not an acceptance run; confirm latency failed §9.
- The 0% wait persisted until roughly 58 seconds into this baseline run, consistent with the seeded opening time of +60 seconds; the scenario then completed. The timestamp normalization therefore behaved as intended in this local diagnostic. The code has no dedicated automated test for this JavaScript timestamp parser.
- Existing reported measurements remain diagnostic only: `loadtest/RESULTS.md` records a prior local full run at 303.75 ms confirm p95 and three macOS-host runs at 566.29 / 324.91 / 373.38 ms. None establishes the required Linux reference.
